Plugins and themes

OpenQuire can be extended without forking it: plugins add commands, sidebar panes, tools, export formats and workflow steps, and themes and CSS snippets change how it looks.

Your first plugin

A plugin is one JavaScript module. It exports a manifest describing itself and a default function that receives the API:

export const manifest = {
  id: 'dev.example.word-count',
  name: 'Word count',
  version: '1.0.0',
  apiVersion: 1,
  description: 'Counts the words in the open document.',
  permissions: ['document:read'],
}

export default function activate(api) {
  api.commands.add({
    id: 'count',
    name: 'Count words',
    run: async () => {
      const doc = await api.document.info()
      let words = 0
      for (let page = 0; page < doc.pageCount; page++)
        words += (await api.document.pageText(page)).split(/\s+/).filter(Boolean).length
      await api.ui.notice(`${words} words`)
    },
  })
}

Save it as word-count.js, then in OpenQuire open Settings, Plugins, Install from file. OpenQuire shows what the plugin asks for before anything is installed. The command then appears in the command palette (Ctrl+P), where it can also be given a hotkey.

Two complete examples: csv-export.js adds an export format and a sidebar pane, and review-notes.js adds a dock tool. For editor support, use the type definitions in openquire-plugin.d.ts.

The manifest

FieldMeaning
idUnique, reverse-domain style, such as dev.example.csv-export. Installing a plugin with the same id replaces the old one.
nameShown in Settings and before each command name in the palette.
versionYour plugin's version. Use semantic versioning.
apiVersionThe plugin API version the plugin was written for. Currently 1.
permissionsWhat the plugin needs beyond adding commands and panes. See below.
description, authorOptional, shown when installing.

The manifest must be a plain object: OpenQuire reads it by loading the module once, with no access to anything, before the user decides whether to install.

Permissions and the sandbox

PermissionAllows
document:readReading the open document: its pages, text, search and bytes.
document:writeChanging the open document. Every change is one step the user can undo.
networkUsing fetch, XMLHttpRequest, WebSocket and EventSource.

Each plugin runs in its own Web Worker. It cannot see the page, the user's other files, OpenQuire's storage or other plugins; it can only use the API. Without the network permission the network functions are removed. Calls that touch the document are checked against the permissions the user approved, and fail with an error otherwise.

Users are told to install plugins only from people they trust. Keep permissions to what the plugin really needs: users see them before installing.

API reference

Everything on api that talks to OpenQuire returns a promise. Pages are numbered from 0, and positions are in PDF points from the page's top-left corner.

Commands

api.commands.add({ id, name, workflow?, run })

Adds Plugin name: name to the command palette. Users can assign it a hotkey. With workflow: true, running the command while recording a workflow adds it as a step, so it runs on every file when the workflow is replayed, with document calls acting on each file in turn.

Panes

api.panes.add({ id, title, content, onEvent? })
api.panes.update(id, content)

Adds a tab to the left sidebar. Content is a list of elements that OpenQuire draws in its own style, in light and dark:

ElementFields
headingtext
texttext, muted?
listitems (strings)
inputid, label, value?, placeholder?
buttonid, label, primary?

When a button is pressed, onEvent receives { element, values }: the button's id and the current value of every input, by id.

Tools

api.tools.add({ id, name, onClick })

Adds a tool to the dock. While it is selected, clicking a page calls onClick({ page, x, y }).

Notices and downloads

api.ui.notice(text)
api.ui.download(name, data, type?)

notice shows a message in the status bar. download offers a file to the user (a save dialog in the desktop app); this is how a plugin adds an export format.

Workflows

document.runStep accepts the steps OpenQuire's workflows use, so a plugin can do anything a workflow can:

await api.document.runStep({ action: 'rotate', pages: 'even', delta: 90 })
await api.document.runStep({ action: 'markPatterns', patterns: ['[\\w.+-]+@[\\w-]+(\\.[\\w-]+)+'] })
await api.document.runStep({ action: 'applyRedactions' })
await api.document.runStep({ action: 'stamp', pages: 'all', stamp: {
  template: 'ACME-{bates}', position: 'br', size: 9, color: [0, 0, 0], opacity: 1, angle: 0 } })

Available steps: rotate, deletePages, stamp, markTerms, markPatterns, applyRedactions, flatten, sanitize, setMeta, detectFields and tag. Their fields are in the type definitions. Page sets are "all", "odd", "even" or ranges such as "1-3, 5".

Workflow files that use plugin commands contain steps like { "action": "plugin", "plugin": "dev.example.csv-export", "command": "export" }. They run in the app with the plugin installed; the command-line tool reports that the plugin is needed.

Themes and snippets

A theme is a CSS file imported in Settings, Appearance; a snippet is a smaller piece of CSS that can be turned on and off. Both are added after OpenQuire's own styles. Build on the design tokens rather than fixed colors, and both light and dark will work:

/* A flatter, square dock */
.dock { border-radius: 4px; box-shadow: none; border-color: var(--border-hover); }

/* A warmer workspace background in the light theme */
.theme-light { --bg-primary: #fbf8f2; }

/* The accent hue comes from Settings; a theme that insists on its own needs !important */
.app { --accent-h: 212 !important; }
TokenUse
--accent-h, --accent-s, --accent, --accent-hover, --accent-softThe accent color, built from its hue and saturation
--bg-primary, --bg-primary-alt, --bg-secondary, --bg-secondary-altBackgrounds of the workspace and sidebars
--text-normal, --text-muted, --text-faintText colors, from strongest to weakest
--border, --border-hover, --border-focusBorders
--hover, --active, --interactive, --interactive-hoverControls
--radius-s, --radius-m, --radius-lCorner radii
--font-interface, --font-mono, --font-small, --font-smaller, --font-mediumType
--header-height, --ribbon-widthLayout

Useful class names: .app (with .theme-light or .theme-dark), .ribbon, .sidebar, .tab-bar, .view-header, .desk, .page, .dock, .status-bar, .modal. Class names are not part of the stable API; tokens are.

Versioning

OpenQuire follows semantic versioning from 1.0. The plugin API has its own version, which plugins declare as apiVersion:

  • Within API version 1, changes only add: new methods, new optional fields, new pane elements and new workflow steps. A plugin written for version 1 keeps working in every OpenQuire release that provides version 1.
  • Removing or changing anything a plugin may rely on means a new API version. OpenQuire refuses plugins written for a version it does not provide, with a message saying which version is needed, rather than running them incorrectly.
  • The design tokens above are stable within a major version of OpenQuire. Class names and the DOM structure may change in any release.
  • Workflow files have their own version field, versioned the same way.
